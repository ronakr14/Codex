Data Partitioning

Partitioning divides a large dataset into smaller logical or physical units using one or more keys. It is primarily a data organization and management technique that can improve query performance, parallel processing, and lifecycle operations.

The important distinction is that database table partitions, storage partitions, and execution partitions are not the same thing. Their implementations and performance implications differ by platform.

1. Why Partition Data?

Partitioning can help with three broad objectives:

  • Query efficiency: Eliminate irrelevant partitions before reading their data.
  • Data management: Isolate data for retention, archival, deletion, and maintenance.
  • Scalability: Organize large datasets into manageable units that storage and compute engines can process.

Partitioning is not automatically beneficial. It introduces metadata, planning, file-management, and operational overhead. Its value depends on whether the data layout matches actual access patterns.

2. Partitioning Models

Range partitioning

Common use cases:

  • Time-series data
  • Transaction history
  • Event and log data
  • Data retention by date

Range boundaries should reflect query patterns and lifecycle requirements.

List partitioning

Assigns records to partitions based on explicitly defined values.

Useful when a known set of categories has operational or query significance.

Hash partitioning

Uses a hash function on a partition key to distribute records across a fixed number of partitions.

Conceptually:

Useful when distributing records more evenly is important and there is no natural range or category boundary.

Hash partitioning does not guarantee perfectly equal partition sizes.

3. Partition Pruning

Partition pruning is the process of excluding partitions that cannot contain records satisfying a query predicate.

Consider a table partitioned by sale_date:

If the table has monthly partitions, the engine may only need to access the June 2026 partition.

Conceptually:

Pruning reduces the amount of data that needs to be considered. The actual amount of I/O avoided depends on the engine, metadata, predicate, and physical layout.

Partition pruning versus predicate pushdown

These are related but different optimizations.

  • Partition pruning: Excludes entire table or storage partitions.
  • Predicate pushdown: Pushes filters closer to the data source so filtering can happen before unnecessary data is fully processed.
  • Data skipping: Uses metadata such as minimum and maximum values or Bloom Filters to skip files, row groups, or other data units where supported.

A query can benefit from more than one of these techniques.

4. Partitioning vs Indexing vs Clustering

These techniques solve different data-access problems.

TechniquePrimary purpose
PartitioningDivide data into manageable physical or logical units
IndexingProvide an access structure for locating records
Clustering / sortingImprove physical locality of related records
Data skippingExclude data units using metadata
Predicate pushdownApply filters closer to the data source

They can complement each other, but they are not interchangeable.

For example, a PostgreSQL table may use range partitioning and indexes within its partitions. A lakehouse table may use directory partitioning, Parquet statistics, and clustering.

Query execution

PostgreSQL can prune partitions that cannot satisfy the predicate.

Partition pruning can happen during query planning and, in supported cases, during execution.

Partition maintenance

Partitioning can simplify lifecycle operations.

For example, an old partition can be detached or dropped rather than deleting a large volume of individual rows.

However, partition maintenance must account for:

  • Foreign keys and uniqueness requirements
  • Dependencies and permissions
  • Retention policies
  • Indexes on partitions
  • Locking and operational impact

Partition-count considerations

There is no universal ideal number of PostgreSQL partitions.

A large number of partitions can increase:

  • Query planning time
  • Memory consumption
  • Metadata overhead
  • Maintenance complexity

The impact depends on how many partitions remain relevant to typical queries and how many partitions each session accesses.

PostgreSQL’s documentation notes that hierarchies containing a few thousand partitions can be manageable when queries prune most of them. This is not a general performance guarantee.

Delta Lake

Delta Lake supports partitioned tables using partition columns.

Example:

A partitioned Delta table stores data files in a partitioned directory layout. The Delta transaction log tracks the active table state, including file and partition information.

Delta Lake adds transactional metadata and file-level statistics to the underlying Parquet storage.

These mechanisms support operations such as:

  • Partition pruning
  • File-level data skipping
  • Transactional updates and deletes
  • Consistent table snapshots

Important: Delta Lake transactions are not defined by directory partition boundaries. Partitioning is a physical data-layout choice, not a requirement for transaction atomicity.

Databricks and modern table layout

Traditional partitioning is not always the best choice for modern Databricks tables.

Databricks currently recommends liquid clustering for new managed tables. Its guidance states that most tables below 100 TB do not need traditional partitioning and recommends considering custom partitioning only when it demonstrates an advantage.

These recommendations are specific to Databricks-managed workloads and should not be treated as universal thresholds for all storage engines.

Liquid clustering:

  • Organizes data using selected clustering keys.
  • Supports changing clustering keys as workloads evolve.
  • Can work with high-cardinality columns and skewed data.
  • Replaces traditional partitioning and Z-Ordering for tables using that layout.

Liquid clustering is not compatible with traditional partitioning or Z-Ordering on the same table.

See Z-Ordering for the separate multi-dimensional data-layout technique.

Why the distinction matters

  • Storage partitioning influences how data is laid out and selected for reading.
  • Execution partitioning influences how work is distributed across tasks.
  • Repartitioning a DataFrame can trigger a shuffle.
  • Writing a partitioned dataset can create directory structures based on partition-column values.

Do not use partitionBy() and repartition() as if they were equivalent operations.

9. Choosing Partition Keys

Partition-key selection should be driven by workload evidence rather than generic rules.

Evaluate:

  • Which columns appear frequently in query filters?
  • What is the cardinality of candidate columns?
  • How large will each partition become?
  • Is the data distribution skewed?
  • Do queries access a small subset of the data?
  • Does partitioning simplify retention or maintenance?
  • Will the layout create too many small files?
  • How frequently does the dataset change?

Common examples

WorkloadPotential partition key
Event analyticsEvent date
Financial transactionsTransaction date
LogsEvent date
Retail analyticsBusiness date
Regional reportingRegion, where justified by volume and access patterns

These are candidate choices, not prescriptions.

High-cardinality columns

Columns such as customer_id, email, and UUIDs can create an excessive number of storage partitions.

For example, partitioning a lakehouse table by customer_id may produce many small directories and files.

For high-cardinality access patterns, consider alternatives such as:

  • Indexes in database systems
  • Clustering
  • Liquid clustering in Databricks
  • Sorting and file-level statistics
  • Hash-based distribution for execution workloads

10. When Not to Partition

Partitioning may not be worthwhile when:

  • The dataset is small.
  • Queries regularly scan most or all of the data.
  • Candidate keys create too many small partitions.
  • Data distribution is heavily skewed.
  • Query predicates do not align with the partition key.
  • Metadata and maintenance overhead exceed the read-performance benefit.

A partitioned table is not inherently faster than an unpartitioned table.

A poor partition strategy can make performance worse and create expensive data-reorganization work.

11. Troubleshooting Partition Performance

When queries are slow despite partitioning, investigate the actual execution behavior.

Step 1: Understand the physical layout

Check:

  • Partition columns
  • Number of partitions
  • Data volume per partition
  • File count and file sizes
  • Data skew
  • Whether the layout reflects actual query patterns

Step 2: Verify pruning

Run representative queries and inspect the query plan.

Look for:

  • Partitions selected
  • Partitions eliminated
  • Files scanned
  • Bytes read
  • Row groups skipped
  • Filters applied at the scan level

The names and visibility of these metrics vary by engine.

Step 3: Review predicates

Prefer predicates that directly express the relevant partition range.

For example:

If a query wraps a partition column in a function, the engine may be unable to use the partition metadata as effectively.

Do not assume every expression prevents pruning; verify the actual plan.

Step 4: Check file layout

A table can have effective partition pruning and still perform poorly because of:

  • Small files
  • Too many files
  • Skewed partitions
  • Poor data locality
  • Ineffective statistics

Compaction and clustering may help, depending on the platform.

Step 5: Validate with measurements

Compare representative workloads before and after layout changes.

Useful metrics include:

  • Query duration
  • Partitions and files scanned
  • Bytes read
  • Rows scanned versus rows returned
  • Task count and task-duration distribution
  • Shuffle volume
  • File count and storage overhead
  • Maintenance duration

Avoid treating a single benchmark as proof of a general improvement. Use representative queries and repeat measurements under comparable conditions.

12. Practical Decision Framework

RequirementConsider
Isolate old data for deletion or archivalRange partitioning
Prune large date-filtered datasetsStorage partitioning, where appropriate
Distribute records across a fixed number of groupsHash partitioning
Improve access to individual recordsIndexing
Improve file-level data localityClustering or sorting
Distribute compute workExecution partitioning
Support changing query patterns in DatabricksLiquid clustering

The decision should be based on workload characteristics, storage behavior, engine capabilities, and maintenance cost.

Key Takeaways

  • Partitioning is a data organization strategy, not a universal performance switch.
  • Database partitions, storage partitions, and execution partitions are different concepts.
  • Partition pruning reduces the data considered by a query when predicates align with partition boundaries.
  • Indexing, clustering, data skipping, and predicate pushdown solve related but distinct problems.
  • High-cardinality partition keys can create excessive small partitions and files.
  • PostgreSQL and lakehouse platforms implement partitioning differently.
  • Modern Databricks guidance favors liquid clustering for new managed tables rather than defaulting to traditional partitioning.
  • Always validate a partitioning strategy against representative workloads.
