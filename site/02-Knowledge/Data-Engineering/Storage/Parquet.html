Parquet

Apache Parquet is an open-source, columnar file format designed for analytical workloads. It stores data by column within row groups and includes metadata, statistics, encodings, and compression information that allow query engines to read relevant data efficiently.

Parquet is a file format, not a database or table format. Technologies such as Delta Lake and Apache Iceberg add table-level capabilities on top of data files, commonly Parquet.

This provides several advantages:

  • Column pruning: Read only the columns required by a query.
  • Compression: Similar values stored together often compress effectively.
  • Predicate pushdown: Use metadata and statistics to avoid reading irrelevant data.
  • Parallel processing: Query engines can distribute work across files and row groups.
  • Interoperability: Multiple engines can read the same Parquet files.

Parquet file architecture

A Parquet file has a defined physical layout:

The footer contains the file schema and metadata describing row groups, column chunks, encodings, compression, and relevant statistics.

Readers can locate the footer from the end of the file. They use this metadata to determine which data regions are relevant before reading the actual column data.

The footer is not a separate database index. It is structural metadata embedded in the file.

Physical hierarchy

The main hierarchy is:

Row groups

A row group is a horizontal partition of the rows in a Parquet file. Each row group contains one column chunk for each column in the schema.

Row groups provide a useful boundary for reading, writing, metadata collection, and query planning.

Important considerations:

  • Larger row groups can improve compression and reduce metadata overhead.
  • Smaller row groups can provide finer-grained pruning opportunities.
  • Row-group sizing affects memory requirements, write performance, and scan parallelism.
  • Query-engine scheduling behavior determines how row groups are actually assigned to tasks.

A row group is not universally equivalent to one Spark task or one unit of parallelism. Execution behavior depends on the engine, file layout, scan implementation, and available parallelism.

There is no universally optimal row-group size. Benchmark representative workloads rather than treating a fixed size as a rule.

Column chunks

A column chunk contains the data for one column within one row group.

For example:

Column chunks allow a reader to access selected columns without reading every column in the row group.

Column-chunk metadata also describes the data region, compression codec, encodings, and available statistics.

Pages

Column chunks are divided into pages.

Pages are the units to which Parquet applies encoding and compression. A reader generally processes page data when reading a column chunk.

Page-level pruning and selective reads can be supported by additional metadata, such as column indexes and offset indexes, when writers produce them and readers understand them.

Do not assume every Parquet file contains page indexes or that every query engine uses them.

Encoding strategies

Parquet supports multiple encoding strategies. The writer can choose encodings based on the data and implementation.

Dictionary encoding

Dictionary encoding is useful when values repeat frequently.

Example:

The dictionary and encoded values reduce repeated storage.

It is particularly useful for low- or moderate-cardinality columns, although the benefit depends on dictionary size and data distribution.

High-cardinality columns may cause dictionary encoding to consume more memory or become ineffective. Writers can fall back to other encodings.

Run-length encoding and bit-packing

Run-length encoding represents repeated values as runs.

Bit-packing stores small integer values using fewer bits than a full-width integer representation.

Parquet uses a hybrid RLE/bit-packing encoding in relevant contexts, including dictionary-encoded data.

Delta encoding

Delta encoding stores differences between successive values rather than storing every value independently.

This can be effective for ordered numeric values and timestamps.

Other encodings

Parquet also supports encodings such as:

  • Plain encoding.
  • Delta binary packed encoding.
  • Delta length byte array encoding.
  • Delta byte array encoding.
  • Byte stream split encoding.

The appropriate encoding depends on the data type, distribution, writer implementation, and reader compatibility.

Encoding and compression are separate concepts: encoding changes the representation of values, while compression further reduces the encoded data size.

Compression

Parquet supports multiple compression codecs. Compression is applied to page data.

CodecGeneral characteristics
SnappyFast compression and decompression; commonly used for balanced workloads
GZIPHigher compression in many cases, with greater CPU cost
Zstandard (ZSTD)Configurable compression levels and a useful balance of speed and compression
BrotliCan provide high compression, depending on data and configuration
LZ4Fast compression and decompression
UncompressedNo compression; useful for particular workloads or diagnostics

The best codec depends on:

  • Storage cost.
  • Read and write frequency.
  • CPU availability.
  • Network throughput.
  • Data characteristics.
  • Compatibility across writers and readers.

Avoid treating compression ratios or codec rankings as fixed. Benchmark with representative data and query patterns.

Parquet stores compression information at the column-chunk level. Different column chunks can use different codecs.

Statistics and data skipping

Parquet can store statistics such as minimum and maximum values and null counts for column chunks.

These statistics can help query engines determine whether a row group might contain values matching a predicate.

Example:

Suppose the metadata contains:

RG11000050000
RG26000090000
RG3110000150000

A query engine can determine that RG1 and RG2 cannot satisfy the predicate and skip them.

This is a form of metadata-based data skipping.

Important limitations:

  • Statistics may be absent or incomplete.
  • Some statistics may be truncated or unsuitable for particular comparisons.
  • Data types and logical types affect comparison semantics.
  • Reader implementations differ in which statistics they use.
  • Overlapping value ranges reduce the effectiveness of min/max pruning.

Sorting or clustering data can improve the usefulness of min/max statistics by reducing overlap between row groups.

Bloom Filters

Parquet supports optional Bloom Filters associated with column chunks.

A Bloom Filter is a probabilistic data structure that can answer whether a value is definitely absent or might be present.

For an equality predicate:

A reader can use the Bloom Filter to determine whether the queried value might exist in a column chunk.

Bloom Filters have no false negatives, but they can have false positives.

They are useful when:

  • Equality predicates are common.
  • Filter columns have sufficiently high cardinality.
  • Min/max statistics are not selective enough.
  • The writer and reader support the relevant Parquet Bloom Filter features.

They are generally not useful for range predicates.

Bloom Filters introduce storage and write overhead. Their effectiveness depends on workload selectivity, filter configuration, and reader support.

A Bloom Filter’s presence in a Parquet file does not guarantee that a particular query engine or library will use it.

See Bloom Filters for the underlying data structure and Parquet Bloom Filters for Row-Group Pruning — ADR for the design decision around their use.

Predicate pushdown and column pruning

Two important optimizations are:

Predicate pushdown: Pass filter conditions to the data source so it can eliminate irrelevant data as early as supported.

Column pruning: Read only the columns required by the query.

For example:

A query engine may:

  1. Read Parquet footer metadata.
  2. Identify the required columns: city and salary.
  3. Evaluate available statistics and other supported pruning metadata.
  4. Skip irrelevant row groups or column chunks where possible.
  5. Read the necessary page data.
  6. Apply remaining filter conditions.
  7. Return the required result.

The exact execution sequence depends on the engine and its reader implementation. Metadata-based pruning is not a guarantee that all irrelevant data can be eliminated.

Nested data support

Parquet supports nested structures such as structs, lists, and maps.

For example:

Parquet uses definition levels and repetition levels to represent optional and repeated nested fields.

  • Definition levels describe how much of a nested field path is defined.
  • Repetition levels describe repeated structure boundaries.

These mechanisms allow nested data to be stored efficiently without requiring every record to have identical nested structures.

They are central to understanding Parquet’s support for complex schemas.

Practical tuning considerations

Write-side considerations

  • Choose row-group sizing based on data volume, query selectivity, memory, and parallelism.
  • Avoid generating excessive small files.
  • Consider sorting or clustering data when it improves compression and statistics-based pruning.
  • Choose compression codecs based on measured CPU, storage, and scan trade-offs.
  • Monitor dictionary encoding behavior for high-cardinality columns.
  • Enable Bloom Filters selectively when equality-filter workloads justify their cost.
  • Validate writer and reader compatibility.

Read-side considerations

  • Select only the columns required by the query.
  • Apply filters early.
  • Use partition pruning where appropriate.
  • Inspect whether statistics are available and useful.
  • Check whether the engine uses page indexes or Bloom Filters before assuming they improve performance.
  • Evaluate file sizing and request overhead for object storage.
  • Inspect the physical execution plan and scan metrics.

Parquet in the Lakehouse

Parquet is commonly used as the physical data-file format in lakehouse architectures.

The responsibilities are different:

  • Parquet: Physical columnar data representation.
  • Delta Lake / Iceberg: Table-level metadata, transactions, snapshots, schema evolution, and related table operations.
  • Query engine: Query planning, execution, optimization, and data access.
  • Storage layer: Durable storage of the underlying files and metadata.

This separation is important when designing and troubleshooting lakehouse systems.
