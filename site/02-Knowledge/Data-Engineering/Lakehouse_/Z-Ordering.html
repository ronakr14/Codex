Z-Ordering

Z-Ordering is a multi-dimensional data-layout technique used by Delta Lake to colocate related records in the same set of data files.

Its primary purpose is to improve data skipping: when a query filters on selected columns, better data locality can make file-level statistics more selective, allowing the query engine to skip files that cannot contain matching records.

Z-Ordering does not directly accelerate query execution. It reorganizes data so that existing pruning mechanisms can eliminate more unnecessary reads.

Multi-dimensional ordering

Ordinary sorting establishes an ordering based on one or more columns. With multiple columns, earlier sort keys receive priority.

Z-Ordering uses a space-filling curve to map multiple dimensions into a single ordering.

For example, consider records represented by two dimensions:

Conceptually, each record is a point in a two-dimensional space.

Z-Ordering interleaves bits from the values of the dimensions to generate an ordering that attempts to preserve locality when the data is mapped into a one-dimensional sequence.

The Z-shaped traversal pattern is the origin of the name.

This is a conceptual explanation. Real implementations must account for column types, value ranges, encoding, and the implementation’s ordering algorithm.

Why locality improves data skipping

Delta Lake collects data-skipping statistics for data files, including information such as minimum and maximum values.

Multiple columns allow the layout to consider more than one query dimension.

However, the effectiveness of locality decreases as additional columns are included. Choosing too many columns can dilute the benefit for individual predicates while increasing optimization work.

Choose columns based on:

  • Frequently executed filter predicates.
  • Query selectivity and data distribution.
  • Whether statistics are collected for the selected columns.
  • The expected benefit compared with the cost of rewriting files.

There is no universal optimal number of Z-Order columns.

Z-Ordering is available in Delta Lake 2.0.0 and above.

Important implementation considerations:

  • OPTIMIZE rewrites data files to improve physical layout.
  • Z-Ordering operates within partition boundaries; files are not combined across different partitions.
  • Z-Ordering is not idempotent. Repeated executions can reorganize data again.
  • It attempts to balance output files by record count, not necessarily by physical file size.
  • The benefit depends on data-skipping statistics being available for the selected columns.
  • Reorganization consumes compute and I/O resources.

See the Delta Lake optimization documentation.

Choosing columns for Z-Ordering

A good candidate is a column that is frequently used in selective query predicates and has statistics available.

For example:

Potential candidates include:

  • Customer or account identifiers.
  • Device identifiers.
  • Product identifiers.
  • Other frequently filtered attributes.

Do not choose columns simply because they have high cardinality or appear in the schema.

Avoid:

  • Columns rarely used in filters.
  • Columns without collected statistics.
  • Excessive numbers of Z-Order columns.
  • Repeated optimization without measuring query improvements.
  • Z-Ordering on partition columns.

A column’s suitability should be evaluated against real query patterns, data distribution, and maintenance cost.

Partitioning versus Z-Ordering

These techniques address different aspects of data layout.

TechniquePrimary role
PartitioningOrganizes data into logical partitions, enabling partition pruning
Z-OrderingImproves multi-dimensional data locality within eligible files and partitions
Parquet statisticsProvide metadata such as minimum and maximum values
Bloom FiltersHelp determine whether a value might exist in a column chunk
Predicate pushdownAllows supported filters to be evaluated closer to the data source

These mechanisms can complement each other, but they are not a fixed sequence of execution steps.

Z-Ordering primarily improves the data layout that file-level statistics can exploit. It does not replace Parquet statistics, Bloom Filters, or predicate pushdown.

Z-Ordering versus liquid clustering

Z-Ordering remains relevant for existing Delta tables and environments that use the OPTIMIZE ... ZORDER BY workflow.

However, the preferred data-layout strategy has evolved.

Databricks recommends liquid clustering for new tables instead of relying on static partitioning and Z-Ordering.

Liquid clustering:

  • Organizes data around selected clustering keys.
  • Supports changing clustering keys as query patterns evolve.
  • Is designed to reduce manual data-layout maintenance.
  • Uses OPTIMIZE to incrementally reorganize data.

Liquid clustering is not compatible with ZORDER BY or traditional partitioning on the same table.

This distinction matters when designing new Databricks lakehouse tables: do not automatically apply an older partitioning-plus-Z-Ordering pattern without evaluating liquid clustering.

See Databricks liquid clustering documentation.

Practical evaluation

Before adopting Z-Ordering, establish a baseline.

Before optimization

Capture:

  • Query execution duration.
  • Files scanned and files skipped.
  • Bytes read.
  • Relevant scan metrics.
  • Current file layout and statistics.
  • Optimization and maintenance costs.

After optimization

Run the same representative queries and compare:

MetricWhat it indicates
Query durationOverall performance impact
Files scannedEffectiveness of file-level skipping
Bytes readReduction in physical data reads
Rows scannedEffectiveness of filtering
OPTIMIZE durationCost of reorganizing the data
Storage changesImpact of rewritten files

Use representative workloads rather than a single idealized query.

A reduction in files read is useful evidence, but the final decision should consider total query performance and the ongoing cost of maintaining the layout.

Mental model

Think of Z-Ordering as a data-layout optimization, not a query index.

The broader lesson is that lakehouse performance depends not only on query plans and compute resources, but also on how data is physically organized.
