1. dbt v2 now ships with DuckDB — and local analytics engineering just got much more serious

DuckDB now ships inside dbt v2, which was released September 14. The new Rust-based dbt engine has a built-in DuckDB adapter, so a local dbt project no longer needs a separate Python adapter installation. More importantly, dbt v2 adds catalog support for DuckLake and Iceberg, queryable Parquet metadata, native SQL comprehension and local column-level lineage. (DuckDB)

The architecture is becoming remarkably clean:

dbt’s metadata itself can now be written as Parquet and queried directly with DuckDB. dbt v2 also performs SQL comprehension and can generate column-level lineage locally, without requiring a dbt platform account. (DuckDB)

Why it matters to you

This is probably the most directly relevant data-engineering development today.

You’re already interested in:

  • Python

  • lakehouse architecture

  • dbt

  • reducing unnecessary cloud dependencies

This gives you a very credible architecture for experimentation:

That’s too simplistic.

3. GitHub’s Security Lab has an autonomous fuzzing agent — and it exposes the real limits of agent autonomy

GitHub published a new Fuzzing Taskflow on September 24 using its Security Lab Taskflow Agent framework.

Point it at a C/C++ GitHub repository and the agent can:

  1. identify fuzzable entry points,

  2. analyze the build system,

  3. create fuzz harnesses,

  4. run AFL++,

  5. inspect coverage,

  6. improve the harness,

  7. triage crashes,

  8. generate vulnerability reports.

The pipeline uses taskflow stages and MCP tools to interact with the underlying fuzzing infrastructure. (The GitHub Blog)

The feedback loop is the interesting bit:

GitHub explicitly warns that the current taskflow executes afl-fuzz, compilers and arbitrary build commands directly on the host, so it should only be run in a disposable environment such as a Codespace or throwaway VM. (The GitHub Blog)

Why it matters to you

This is a fantastic example of agentic engineering done properly conceptually.

The agent isn’t simply producing text.

It operates inside a measurable loop:

action → observation → metric → adjustment → action

That’s the same pattern you should use for your Lakehouse optimizer.

For example:

The difference between a useful agent and an expensive chatbot is often exactly this closed-loop feedback mechanism.

4. Meta’s Private Processing architecture shows what privacy-preserving agent memory could look like

Meta Platforms published a detailed engineering explanation of Private Processing for Meta AI glasses on September 23.

The problem is interesting:

AI glasses need highly personal context, potentially spanning conversations and days or weeks, but much of the model computation cannot fit on-device.

Meta’s solution moves sensitive processing into confidential virtual machines (CVMs) using trusted execution environments. The client performs remote attestation before sending data, and the host infrastructure—including Meta’s operators—cannot access plaintext inside the protected environment. (Engineering at Meta)

The more interesting part is persistent memory:

Meta says it also had to redesign observability because normal debugging techniques—memory dumps, debuggers and detailed payload inspection—are incompatible with the confidentiality boundary. Instead it relies on aggregate health signals such as CPU, memory, network latency and hardware failure rates. (Engineering at Meta)

Why it matters to you

This is particularly relevant to your PKM + agent memory interests.

You’ve been thinking about long-lived agents that understand:

  • your notes

  • projects

  • career goals

  • architecture decisions

  • learning history

That creates a nasty security question:

Where should an agent’s long-term memory live?

A local-first architecture gives you one answer:

But if you eventually use cloud inference, confidential computing becomes another architectural option.

The important concept isn’t Meta’s implementation.

It’s moving the trust boundary.

5. AdaCore’s GNAT Foundry demonstrates a different future for AI coding: prove the code instead of trusting the model

AdaCore’s GNAT Foundry: Intersection is an unusually good experimental project for understanding what AI-assisted engineering could look like in high-integrity systems.

The demo gives an AI coding agent a change request for a traffic-light controller and has it update:

The resulting evidence includes formal proof, requirements-based tests, structural coverage and traceability. AdaCore explicitly argues that humans should remain accountable for AI-produced artifacts while deterministic tools establish evidence about correctness. (AdaCore)

The project is open source and can be run with the community Ada/SPARK toolchain. AdaCore says the demonstrated change takes about two hours and roughly $50 using frontier AI agents. (AdaCore)

Why it matters to you

This one hits your SDET + software engineering + architecture background directly.

The industry is slowly discovering an uncomfortable truth:

AI makes code generation cheaper.
It does not make correctness cheaper.

In fact, when AI can produce code much faster, verification becomes the bottleneck.

That’s exactly where your SDET experience can compound with your data/AI career.

Think:

That is a far more scalable model than asking humans to manually inspect every line an agent produces.
