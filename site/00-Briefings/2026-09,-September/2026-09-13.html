Daily Engineering Briefing — 13 September 2026

Today’s five are deliberately skewed toward things you can learn from or build with, rather than the usual model-release treadmill. The strongest signal is that the data platform itself is becoming an agent substrate.

1. Databricks expands Genie Agents — and makes structured data a first-class agent tool

Databricks expanded Genie Agents on September 10. Each agent can now use up to 50 tables, views, or metric views, up from 30, while its conversation capacity increased from 10,000 to 200,000 conversations. Databricks also provides a managed Genie Agent MCP server, allowing external agents and tools such as coding assistants to query a curated Genie Agent using natural language while Unity Catalog permissions are enforced on every request. (Databricks Documentation)

The architectural bit I care about is the separation:

Databricks explicitly recommends Genie Agents when an agent needs to query structured Unity Catalog data, while deterministic UC functions can be used where reproducibility matters. (Databricks Documentation)

Why it matters to you

This is very close to the architecture you should be studying for your move from data engineering toward AI architecture.

The important idea is that you don’t let an LLM loose on the entire warehouse.

Instead:

curated context → semantic boundary → governed tool → deterministic execution

That’s a much stronger pattern than generic text-to-SQL.

It also gives you a concrete direction for the Akashic Records:

Markdown/metadata → curated semantic layer → MCP → specialized agents.

And for your Lakehouse Copilot:

workload metadata → optimizer context → controlled tools → actions.

Practical experiment: expose a small DuckDB/Postgres dataset through an MCP server and deliberately restrict the agent to a curated schema. Measure how much accuracy improves when the context boundary is narrower.

Source: Databricks Genie Agent documentation · Databricks Genie MCP documentation

2. Meta demonstrates the next step: agents optimizing production systems themselves

A fascinating engineering post from Meta describes ZGateway, a new proxy tier placed in front of ZippyDB. More interestingly, Meta says many of the system’s existing operational heuristics—load shedding, balancing, failover, cache bounds and batch windows—already behave like control loops. The team is now considering exposing those decisions and telemetry as a structured control surface that AI agents can observe and operate under guardrails. (Engineering at Meta)

This builds on Meta’s earlier KernelEvolve, which autonomously explores kernel implementations and reported a 60% improvement in ads-model inference throughput in its production experimentation. (Engineering at Meta)

Why it matters to you

This is a much more interesting direction than “AI writes code.”

The emerging architecture is:

That’s essentially closed-loop engineering.

And it maps directly onto your Lakehouse Optimization project.

Your original concept is already heading here:

observe → diagnose → recommend → optimize

The next evolution is:

observe → hypothesize → experiment → measure → decide → apply → verify

That’s far more compelling.

Practical experiment

Build a toy optimizer around a DuckDB workload:

  1. collect query runtime/scan/cardinality metrics,

  2. generate optimization hypotheses,

  3. test candidate indexes/partitioning/query rewrites,

  4. benchmark them,

  5. retain only statistically useful changes.

You’ve now built a miniature version of the same agentic control-loop architecture.

Source: Meta Engineering — ZGateway · Meta Engineering — KernelEvolve

3. Kubernetes 1.37 advances workload-aware scheduling — including AI/accelerator workloads

Kubernetes 1.37’s current release series is introducing several substantial scheduling changes.

The most relevant for AI/data infrastructure is Dynamic Resource Allocation (DRA): DRA Extended Resource support has reached GA, while fractional resource allocation and scheduler improvements are progressing through beta/alpha. Kubernetes reports that a new pre-queueing mechanism can reduce an expensive requeue path from roughly O(N²) to O(1) in the affected scheduling scenario, with early benchmarks showing roughly 2× scheduling throughput. (Kubernetes)

Kubernetes is also introducing workload-aware scheduling improvements specifically in response to AI/ML and complex batch workloads, while node lifecycle conditions are being added as a common API for expressing node state. (Kubernetes)

Why it matters to you

This is where your data engineering → architecture progression becomes relevant.

You don’t need to become a Kubernetes operator.

But you should understand why modern platforms increasingly need to schedule based on:

  • GPU/accelerator availability

  • fractional resources

  • workload groups

  • priority

  • locality

  • capacity

  • failure domains

  • scaling behavior

The architecture question becomes:

Where should this computation run, and what resources should it consume?

That’s relevant to Spark, Databricks, Ray, model serving, batch ETL and agent infrastructure alike.

What I’d learn: DRA + workload-aware scheduling, not Kubernetes YAML trivia.

Source: Kubernetes — DRA updates in 1.37 · Kubernetes — workload-aware scheduling

4. Google commits €13B to Finnish AI infrastructure — power is becoming part of software architecture

Google announced on September 9 that it will invest €13 billion in Finland over 2027–2028, expanding digital infrastructure and data centers while investing in local energy projects and partnerships. Google says the expansion will support demand from services including Gemini and other AI workloads. (blog.google)

The less obvious part is the energy architecture: Google is pairing the infrastructure expansion with electricity-market investments, including its first agreement involving a nuclear plant life extension and uprate, alongside renewable-energy partnerships. (blog.google)

Why it matters to you

This is not primarily a “Google spent lots of money” story.

It’s a reminder that AI infrastructure is ultimately constrained by physical systems:

As you move toward architecture, this systems view becomes increasingly valuable.

A model can be 20% more efficient, but if inference demand grows 10×, the platform still needs dramatically more compute.

That means architecture discussions increasingly include:

  • utilization

  • power efficiency

  • accelerator selection

  • cooling

  • network topology

  • workload placement

  • cost per inference

This also connects nicely to the Kubernetes scheduling story above.

Source: Google — €13B Finland AI infrastructure investment

5. Meta’s “Organizational Second Brain” is unusually relevant to your PKM project

This is the most directly relevant niche item today.

Meta published details of an Organizational Second Brain on September 2. The system is designed to preserve specialist knowledge by separating what the system knows from how it reasons. Expert corrections are compiled into verified, regression-tested updates to the knowledge base without retraining the underlying model. (Engineering at Meta)

Meta describes two central layers:

  1. a structured, auditable knowledge architecture, and

  2. a self-improvement loop that turns expert feedback into persistent, tested knowledge.

Why it matters to you

This is remarkably close to what you’ve been designing for The Akashic Records:

  • knowledge graph

  • note quality scoring

  • freshness

  • connectedness

  • confidence

  • agent workspace

  • expert feedback

  • reusable knowledge

  • regression/testing of knowledge

The important distinction is:

Don’t teach the model everything. Build a system that can maintain knowledge outside the model.

That is a very strong PKM architecture principle.

Your existing idea of promoting notes from Reference → Curated → Evergreen could become much more powerful if each promotion also generated a machine-checkable knowledge artifact and regression tests.

For example:

That’s effectively CI/CD for institutional knowledge.

And honestly, this is one of the more interesting directions for your PKM project than simply adding another vector database.

Source: Meta Engineering — An Organizational Second Brain

What I’d pay attention to today

1. Meta’s ZGateway + KernelEvolve

This is the most important architectural pattern in today’s briefing.

The interesting future isn’t merely:

“AI writes software.”

It’s:

AI participates in the engineering control loop.

Observe → hypothesize → experiment → measure → modify → verify.

That’s directly applicable to your Lakehouse Copilot and gives you a much stronger architecture to pursue.

2. Databricks Genie Agent + MCP

This is the one I’d actually try.

Build a miniature version locally:

DuckDB/Postgres → curated semantic schema → MCP → agent → SQL → validation

Then add permissions and deterministic functions.

That gives you a compact but serious project combining data engineering, context engineering, MCP, agents, governance and evaluation.

Today’s bigger pattern

The five stories are surprisingly connected:

Databricks is putting governed data behind agents.
Meta is putting production control loops behind agents.
Kubernetes is making infrastructure resource-aware enough to run those workloads.
Google is scaling the physical infrastructure underneath them.
Meta’s Second Brain is showing how structured knowledge can become a persistent layer outside the model.

That’s the architecture I’d keep in your head:

Data + Knowledge + Agents + Control Loops + Infrastructure

That’s a much more durable skill stack than chasing whichever model happened to top a benchmark this week.
